# Job discovery: platform access and practical boundaries

Research date: 23 October 2026. First-party documentation was retrieved directly or through the search index on that date. Search crawl timestamps are not publication dates. This is an engineering access assessment, not a claim of complete platform coverage or legal advice. No account creation, authenticated access, API purchase, bulk collection, or external mutation was performed.

## Evidence and interpretation

**LinkedIn.** The [API access catalog](https://learn.microsoft.com/en-us/linkedin/shared/authentication/getting-access) lists open identity/sharing permissions and approved Talent programs. Its [posting endpoint documentation](https://learn.microsoft.com/en-us/linkedin/talent/job-postings/api/sync-job-postings?view=li-lts-2025-07) describes job-management operations; [program terms](https://www.linkedin.com/legal/l/job-posting-api-terms) require vetting and approved use cases. Therefore “no public search API confirmed” is supported; “LinkedIn cannot contribute leads” is not. Native [job search](https://www.linkedin.com/help/linkedin/answer/a511260/linkedin-help-center?lang=en) remains useful to the user. LinkedIn [prohibits scraping/automation software](https://www.linkedin.com/help/linkedin/answer/a1341387/prohibition-of-scraping-software?lang=en); access to a user session is not permission to crawl it.

**X.** [Official search documentation](https://docs.x.com/x-api/posts/search/introduction) specifies time windows, pagination and operators. A useful query family combines role synonyms with hiring phrases, location/remote terms, author lists and links; deduplicate by Post ID and resolve linked employer openings. That query strategy is an engineering recommendation, not a documented guarantee of recall. [Pricing documentation](https://docs.x.com/x-api/getting-started/pricing) currently describes pay-per-use credits, endpoint-dependent rates and spending limits. Avoid stale fixed-tier price assumptions. A distinct [xAI X Search tool](https://docs.x.ai/developers/tools/x-search) also offers keyword/semantic search and thread fetching with separate billing; evaluate its source fidelity and economics separately from the direct X API.

**Indeed.** The [current documentation catalog](https://docs.indeed.com/) distinguishes job/candidate/employer integrations and identifies Indeed PLUS as Japan-focused. The [Publisher plugin documentation](https://docs.indeed.com/indeed-plus/publisher-js-plugin), updated 26 June 2026, explicitly supports candidate job search with query/location filters and partner-provided identifiers. This is a meaningful route, but does not establish permission to ingest its results into an independent matching database. An old publisher client or historical tutorial is insufficient evidence of current unrestricted backend access. Ask the partner team about approved aggregation/feed options and target-country coverage.

**Glassdoor.** The [legacy developer page](https://www.glassdoor.com/developer/index.htm) returned 404; the [official API help article](https://help.glassdoor.com/s/article/Glassdoor-API?language=en_US) could not be read beyond a loading/CSS error. Third-party claims that partnerships have ended were not adopted as first-party-confirmed facts. [Current terms, section 4.3](https://www.glassdoor.com/about/terms/), are readable and materially constrain automated collection and reuse. Employer-side products or analytics are not evidence of a public jobs feed. A licensed arrangement remains an inquiry, not an implemented capability.

**Forums and Medium.** [Reddit search documentation](https://www.reddit.com/dev/api/#GET_search) establishes technical capability; [access guidance](https://support.reddithelp.com/hc/en-us/articles/14945211791892-Developer-Platform-Accessing-Reddit-Data) and [Data API Terms](https://redditinc.com/policies/data-api-terms) establish approval and commercial-contract boundaries. Generic forums need individual assessment: a public RSS feed or documented API is preferable to guessing hidden endpoints. [Medium’s feed guide](https://help.medium.com/hc/en-us/articles/214874118-Using-RSS-feeds-of-profiles-publications-and-topics) documents concrete feed patterns, including `medium.com/feed/@username` and `medium.com/feed/tag/<tag>`.

**Canonical jobs.** [Greenhouse Job Board API](https://docs.greenhouse.io/job-board.html) and [Lever’s official Postings API](https://github.com/lever/postings-api) are examples of employer-origin discovery. The user clarified that “HotJobs” did not identify a particular website; it creates no source requirement or blocker.

## Recommended order

1. Build discovery around employer career pages/documented board endpoints, selected RSS feeds, search-provider results and user-supplied URLs/text. Search indexing is a lead source with incomplete coverage and stale snippets, not permission to reproduce a platform corpus. Validate each lead against its canonical employer source where possible.
2. Add X with an approved account and explicit spending budget; evaluate Reddit approval separately. Extract hiring intent, evidence URL, timestamps and linked openings; retain uncertainty when a social announcement has no confirmed vacancy.
3. Treat LinkedIn/Indeed/Glassdoor as separate access negotiations and assisted discovery channels. Record adapter states such as available, credentials required, partner approval required, unsupported use, or temporarily inaccessible. A blocked page is an observation about one route, not a conclusion that discovery is impossible.
4. Preserve provenance and freshness: source URL, discovered time, published time when explicit, last verified time, canonical opening, and access method. Distinguish raw opportunities, plausible hiring signals, verified open roles and expired/unknown status.

Prefer source selection by marginal relevant coverage, freshness and eligibility over raw job counts. Google/web search should expand employer and board URLs with role synonyms, location variants and hiring phrases; indexed visibility is not authorization to bulk mirror source content. Store each adapter’s access state, attribution rules, last successful refresh and source-specific delay so matching never presents a delayed feed as real-time coverage.

Himalayas contract caveat: the [hosted OpenAPI](https://himalayas.app/docs/openapi.json) specifies `locationRestrictions` as objects `{alpha2,name,slug}` and timezone offsets as strings; its older official GitHub example describes country strings and numeric offsets. The landing guide and schema also differ on whether no timezone restriction uses all offsets or an empty array. Use server-side country filters, a tolerant validated decoder, and a bounded contract check before production. Missing restriction fields mean unknown, not worldwide. Preserve raw restrictions. `pubDate` means last updated in current schema, and salary numbers use `salaryPeriod`, not necessarily annual units. These uncertainties affect eligibility and freshness ranking.
