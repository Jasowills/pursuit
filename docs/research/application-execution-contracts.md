# Application execution and job-linked follow-up contracts

Research date: 2026-10-23. Primary documentation only. No account login, external submission, email or DM was performed. These are integration findings and implementation recommendations, not proof that Pursuit already executes the routes.

## The main boundary

Public job discovery and application submission are different permissions. A candidate can use a hosted application form without possessing the employer's integration key. That does **not** make the employer's server-side submission API anonymously available to Pursuit.

| Provider   | Documented read/apply contract                                                                                                                                                                                                         | Consequence for Pursuit                                                                                                                                                                                 |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Ashby      | `applicationForm.submit` requires `candidatesWrite`; the documented API uses Basic authentication. Custom-careers flow retrieves job-specific form definitions, then submits named field paths.                                        | Recognize Ashby URLs, retain its hosted application URL, and use an explicitly supported hosted-form adapter or handoff. Do not claim arbitrary-employer API submission without authorized credentials. |
| Greenhouse | Job Board GET endpoints are public. Application POST requires the employer's Job Board API key using Basic Auth. Required-question validation is the client's responsibility; the API can accept applications missing required fields. | Discover publicly, but validate the actual form and candidate answers before any submit. A successful transport response alone cannot establish that the complete intended answers/files were recorded. |
| Lever      | Hosted application URL is returned as `applyUrl`. POST needs an API key generated by the employer account's Super Admin. Configurable fields apply; resume upload needs multipart.                                                     | Prefer the hosted form route for a candidate-owned product. Never obtain a key by extracting a site's internal/browser configuration.                                                                   |

These consequences are engineering inferences from the documented boundaries, not additional access grants.

### Ashby details

The custom careers guide specifies `String`, `Email`, `File`, selections and other field types; required fields and actual paths come from the individual form. A successful submission returns `submittedFormInstance` and `formMessages`. `blocked: true` is a distinct outcome even within a response containing form results. For files, Ashby recommends obtaining a presigned upload handle, uploading bytes with the declared content type/length, then submitting the handle. The URL expires after ten minutes, so upload handles must be created during execution rather than while a packet waits for days. Survey submission follows successful core application submission. API documentation does not establish universal candidate-side permission or an idempotency key. [Submission endpoint](https://developers.ashbyhq.com/reference/applicationformsubmit), [authentication](https://developers.ashbyhq.com/reference/authentication), [custom careers flow](https://developers.ashbyhq.com/docs/creating-a-custom-careers-page), [presigned upload change](https://developers.ashbyhq.com/changelog/2026-04-06-application-form-submit-presigned-file-uploads).

### Greenhouse details

Job-specific `questions` describe the form. Attachment methods include multipart bytes, base64 content, a remote URL and plain text. Direct local bytes avoid exposing a candidate document through a public download URL. The provider recommends its embedded form because validation and spam handling are already implemented. Its API documentation does not promise rejection of incomplete applications and does not document a general client idempotency parameter. Preserve the original response/evidence and validate the selected adapter's actual success behavior. [Job Board API authentication, application and attachment sections](https://docs.greenhouse.io/job-board.html).

### Lever details

The documented POST limit is more than two applications per second, with possible changes; 429 handling/queuing is required for custom employer forms. This is a ceiling, not a throughput target or authorization for mass applications. The documented success response is HTTP 200 with `ok: true` and `applicationId`; HTTP errors use `ok: false`. Capture the application ID when using an authorized API route. Hosted forms handle employer custom configurations and queuing. The documentation does not provide a universal idempotency-key contract. [Official Postings API](https://github.com/lever/postings-api/blob/master/README.md).

## Resolving a shared job link

A URL is a source locator, not a trusted instruction. Schema.org provides `JobPosting.url`, `hiringOrganization`, `validThrough`, `directApply` and `applicationContact`. `applicationContact` means a job-relevant information contact, not necessarily an address accepting applications. `directApply` indicates a clear online route; it is not permission to automate that route. Applicant location restrictions also do not represent citizenship or visa rights. [JobPosting definition](https://schema.org/JobPosting).

Google's publisher guidance requires actual job-detail content, correct expiry treatment and an application option. It distinguishes direct application from indirect routes. This is useful validation evidence, not a candidate-submission API or an authentication bypass. [JobPosting publisher guidance](https://developers.google.com/search/docs/appearance/structured-data/job-posting).

Recommended resolver contract:

1. Retain original URL, final validated URL, provider/posting identity and evidence excerpts.
2. Resolve an employer-owned canonical listing or an approved ATS route. For inaccessible LinkedIn/X posts, accept user-pasted job text and separately verify an employer link; do not fabricate details from the URL slug.
3. Record application route as `hosted_form`, `explicit_email_instruction`, `authorized_api`, `manual_or_unknown`, with its source and timestamp. An email found somewhere on a company page is insufficient to choose email application.
4. Keep job content untrusted; never execute embedded instructions, arbitrary scripts or model-selected endpoints.
5. Recheck freshness and the route before execution. Login, CAPTCHA, unknown mandatory answers, legal attestations and ambiguous application instructions become user tasks.

## Email applications and evidence

Gmail requires an authorized account/scope. Messages use RFC 2822 MIME encoded as base64url; attachments are MIME parts. `users.messages.send` returns a `Message` resource with an immutable message ID and thread ID. Save those provider identifiers, recipient, exact content/document hashes and time. They establish provider acceptance, not delivery to a recruiter, reading, an ATS application ID or an interview. A timeout after send is an uncertain outcome, not proof that no email was sent. [Sending guide](https://developers.google.com/workspace/gmail/api/guides/sending), [send endpoint](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/send), [Message resource](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages).

For a real reply, Gmail threading requires a matching subject, target `threadId`, and appropriate `References`/`In-Reply-To` headers. Do not claim a fresh introduction is an existing conversation. [Threading contract](https://developers.google.com/workspace/gmail/api/guides/threads).

## Job-linked people and follow-up

LinkedIn's self-service permissions cover identity and social posting; they do not establish general member-DM or recruiter-search access. LinkedIn explicitly restricts third-party website scraping and automated activity. Build a reviewed message that a user can copy, with a verified public profile reference, rather than a logged-in website bot or a claimed sent/draft state. [API permission catalog](https://learn.microsoft.com/en-us/linkedin/shared/authentication/getting-access), [automated activity guidance](https://www.linkedin.com/help/linkedin/answer/a1340567/automated-activity-on-linkedin?lang=en), [User Agreement](https://www.linkedin.com/legal/user-agreement).

X does offer DM endpoints with authenticated user access, returning DM event/conversation IDs. That is not unrestricted cold-DM permission: the automation rules prohibit unsolicited automated DMs, require recipient intent and opt-out, and say mere technical ability to receive a DM is insufficient. They also prohibit scripting the website. Use user-copyable drafts for this release; an optional future approved API integration needs separate account access and recipient-consent policy. [DM contract](https://docs.x.com/x-api/direct-messages/manage/introduction), [automation rules](https://help.x.com/en/rules-and-policies/x-automation).

Recommended research record: link each person to the specific job/company; store name, current role, source URL, quoted supporting text, observed time, channel URLs and verification status. Prefer employer team pages and the named job contact. A founder is not automatically the relevant recruiter. Never guess email addresses, employment status, personal familiarity or deliverability. An official public email is a published channel, not proof it accepts applications. These are provenance recommendations, not claims of a universal people-search API.

A follow-up draft should use one verified candidate accomplishment and one sourced role/company detail. Before application, avoid saying “I applied.” After application, that assertion needs an actual submission receipt. Copying a message records `copied`, not `sent`; a user's manually reported send should retain that evidence type.

## Execution reliability recommendations

Use durable states: `prepared → needs_input/ready → authorized → executing → confirmed/uncertain/failed`. Bind authorization to candidate identity, canonical role, route, answer set, document hashes and policy revision. An existing bounded auto-apply grant may authorize a supported payload; outreach remains separately approved under Pursuit's product decision.

Reserve daily attempt/submission budgets atomically; lease workers; create a stable candidate + canonical-role intent key. Keep append-only attempt/receipt records. A lease expiry during a potentially completed external POST should become `uncertain`, not automatic re-execution. No reviewed provider contract here proves exactly-once side effects. Reconcile provider evidence or ask the user before retrying an ambiguous send. Safe GETs can retry with bounded backoff; provider-specific rejected/rate-limited submissions need a separately tested retry policy.

Qualification needs controlled hosted-form fixtures for custom fields, multipart resume upload, changed questions, inaccessible pages, receipt evidence, concurrent workers, restart after upload/before submit, budget exhaustion and post-submit timeout. No document review or one successful application can establish production-scale coverage across arbitrary ATSs.
