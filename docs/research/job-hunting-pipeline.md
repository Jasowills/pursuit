# Job discovery, bounded execution and phone companion

Research date: **2026-10-22**. Primary-source capability research and architecture recommendations, not legal advice or live integration qualification. Complements [Desktop, Core and Connect](desktop-core-connect.md) and [runtime research](opencode-runtime-and-models.md); it does not change the approved implementation plan.

## Recommendation

Use an **ongoing bounded pipeline with an initial discovery sweep**, rather than waiting for 300 jobs before preparing anything. A catalog of hundreds of jobs is useful; 300 is not a sensible execution barrier. Start preparing the best eligible roles as soon as enough evidence exists, refill the queue periodically, and keep discovery independent of application execution. All numerical limits below are proposed defaults, not existing behavior.

Give each career track its own role vocabulary, experience evidence, resume variant, eligibility rules and priority. Deduplicate jobs globally while recording the fit and rationale separately for each track. A person pursuing design and frontend development should receive distinct qualification, not a blended generic resume.

| Strategy                              | Benefit                                               | Cost or weakness                                                                        |
| ------------------------------------- | ----------------------------------------------------- | --------------------------------------------------------------------------------------- |
| Gather 300, then process              | Easy one-off snapshot and comparison                  | Delays first action; older jobs can close; encourages paying to analyze irrelevant jobs |
| Continuous discovery without limits   | Fast refresh                                          | Unbounded requests, tokens and queue growth                                             |
| Initial sweep + bounded replenishment | Early useful results, controlled spend, fresher queue | Needs durable scheduling, fairness and freshness state                                  |

Proposed stages: discover → normalize/deduplicate → deterministic eligibility → cheap ranking → limited model review → prepare → authorized execution → verified confirmation → track. Keep separate fetch, model, browser-action and submission budgets. A small ready queue (for example 10–20 qualified jobs) can coexist with hundreds of indexed jobs. Give every active track a minimum discovery allocation, then distribute remaining work by user priority and observed useful yield.

[Terms §4.3](https://www.glassdoor.com/about/terms/)                                                                                                                                                                                                                 | No default scraping adapter. Verify a permitted integration before promising coverage.                                             |

**Recommendation:** seed company-board discovery with explicit user companies, a maintained public-board directory, and optionally a licensed job-search/index provider. Add user-supplied job URLs and permitted feeds. Company careers watchers should be typed source adapters with per-domain concurrency, backoff, conditional requests where supported and recorded polling intervals. Public API availability is not a blanket redistribution license; adapter admission must record supported usage and applicable terms. Do not promise internet-wide crawling, all employers, or real-time updates.

“Active” should mean last successfully observed on the authoritative board at a displayed time, not guaranteed hiring intent. Store source publication date separately from `first_seen`, `last_seen`, `last_checked`, content version and closed status. An interrupted or truncated fetch must not close missing jobs. Recheck shortlisted jobs before expensive preparation and again before execution; failed checks yield unknown freshness. A live listing cannot prove an employer is actively interviewing.

## Spend and model privacy: recommendations

Fetch structured metadata once per board, normalize locally, reject explicit location/authorization/seniority/exclusion mismatches, and hash normalized content. Unknown salary or eligibility is unknown, not an invented positive or automatic rejection. Deduplicate first by provider + board + posting ID and canonical application URL; use employer/title/location fingerprints only to suggest cross-source duplicates, preserving evidence when uncertain.

Rank locally using transparent weighted criteria. Send only a capped shortlist to a model, with the relevant confirmed career facts and compact job text; request structured scores with evidence and unresolved questions. Cache by job content hash, track-profile revision, rubric and model. Reuse an evaluation only while those inputs remain valid. Generate full tailored materials only for selected jobs. Avoid serially placing 300 full descriptions and an entire career history into agent context. A nominal 300 × 2,000-token description pass already means roughly 600,000 input tokens before prompts and output; this is an illustration, not a measured Pursuit workload.

BYOM changes who pays for inference; it does not make inference free or provide scheduling, search, browser execution, provider rate-limit immunity or unlimited context. Enforce attempt limits including failed requests, input/output token ceilings, concurrency limits and provider-side spend caps where available. If cost cannot be measured reliably for a model, show an unknown estimate and enforce token/request limits. Keep keys on the execution host in its secret store; never relay them to the phone.

| Optional service         | Benefit                                                        | Cost/privacy tradeoff                                                                                                              |
| ------------------------ | -------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Licensed jobs/search API | Broader initial coverage and lower adapter maintenance         | Fees, quotas, index lag and contractual coverage limits; search queries leave the device. Verify provenance and permitted storage. |
| Hosted browser executor  | Execution while desktop is offline                             | Recurring compute; session cookies and candidate data enter another trust boundary; adapter reliability still needs qualification. |
| Hosted model             | Stronger inference without local hardware                      | BYOM charges and provider processing of selected career/job data.                                                                  |
| Local model              | Keeps model inputs on the user's machine                       | Hardware, memory, energy and latency costs; context/tool capability must be tested.                                                |
| Encrypted relay/push     | Phone receives approvals without direct inbound desktop access | Hosting/abuse-control cost; relay sees routing/timing metadata even if payloads are encrypted.                                     |

## Companion and background execution

**Facts:** iOS normally suspends background apps; the system schedules refresh and processing work. It is not a guaranteed continuously running job hunter. Android periodic WorkManager has a 15-minute minimum interval and flexible execution timing. [Apple background strategies](https://developer.apple.com/documentation/backgroundtasks/choosing-background-strategies-for-your-app), [Android work requests](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work).

**Recommendation:** keep the phone a companion for review, approvals, pause/revoke, status and notifications. Offer optional QR-paired device identities with no Pursuit account, end-to-end encrypted payloads, device revocation, expiring requests and replay protection. “Accountless” still requires authentication by device keys. A relay queues encrypted messages; it does not execute local jobs. If execution stays on desktop, the desktop must be awake, online and running the worker. A phone approval while it is offline should show “queued,” and execute only after the desktop reconnects, validates approval freshness and rechecks the job. Always-on execution requires a separately disclosed remote worker or user-controlled host. Existing accountless-relay details remain in the Core/Connect research.

**Distribution facts:** TestFlight supports up to 10,000 external testers and 90-day builds, with beta review requirements; it is a beta channel. Google Play internal testing supports up to 100 testers. [Apple TestFlight](https://developer.apple.com/help/app-store-connect/test-a-beta-version/testflight-overview/), [Play testing](https://support.google.com/googleplay/android-developer/answer/9845334). A PWA avoids store beta distribution: on iOS/iPadOS, web push requires a Home Screen web app on 16.4+ and permission requested following direct user interaction. Apple does not require Developer Program membership for this web-push route. [WebKit](https://webkit.org/blog/13878/). A PWA still needs hosting, pairing and a push sender; it is not an always-running worker.

**Recommendation:** validate accountless pairing and mobile review with an installable PWA first, then native TestFlight/Play internal builds when native features justify their maintenance and store release work. Native iOS/Android distribution and push qualification are distinct deliverables from the desktop harness.

## Existing checkout boundary

The [web autopilot](../AUTOPILOT.md) already imports bounded real Greenhouse postings (up to five configured boards, 25 jobs each), applies rule-based qualification and can prepare BYOM drafts through its separate API/database worker. Its configured API/database host must run; automatic application mode is rejected. This is not native desktop source watching.

The [desktop workspace](../CAREER_WORKSPACE.md) stores local career/job records and demonstrates the full journey in isolated sample mode; it does not yet discover jobs, execute applications, send outreach, run source watchers or ship a working companion/relay. The [desktop build](../DESKTOP_BUILD_STATUS.md) has no tray/background worker; closing the native window quits it. [Model connections](../DESKTOP_MODEL_CONNECTIONS.md) and supervised [OpenCode sessions](../DESKTOP_AGENT_RUNTIME.md) exist, but a successful inference or conversation does not establish career-tool execution. No new implementation or live submission was performed for this research.

## Decisions needed before harness work

4. Is broad paid-index coverage optional BYO service access, Pursuit-funded infrastructure, or deferred until direct ATS coverage is measured?
5. Is an installable PWA sufficient for the first companion, followed by native distribution after pairing and approvals work reliably?
