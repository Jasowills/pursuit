# Resume tailoring and document contracts

Research date: 2026-10-23. Primary documentation was read on that date. This note establishes engineering constraints and recommendations, not that these integrations already exist or that a template guarantees hiring success. No real candidate document, Google account or application was accessed.

## Templates: credible guidance, not employer endorsement

Greenhouse identifies multiple-column layouts, complex tables, headers/footers, contact details in text boxes, graphics and image-only resumes as parsing hazards. Its parser rejects resumes over 2.5 MB; an attached file can still require manual field entry if parsing fails. A successful upload is therefore not proof that the ATS extracted the right facts. These are vendor-specific limits, not a universal PDF specification. [Greenhouse parsing guidance](https://support.greenhouse.io/hc/en-us/articles/200989175-Unsuccessful-resume-parse).

Harvard's career service publishes bullet and paragraph templates, accessible DOCX versions, Google Docs references and examples for engineering/technology careers. It encourages concise presentation of relevant evidence and a cover letter connected to the employer. This supports a conventional reference-based template, **not** claims of approval by Harvard, Google, Meta, or any other employer. Reproduce structural principles rather than branding a Pursuit design as an endorsed template. [Harvard resume and cover-letter resources](https://careerservices.fas.harvard.edu/channels/create-a-resume-cv-or-cover-letter/).

Recommended initial Pursuit layouts: a single-column professional resume, an experience-first variant, and an early-career variant. Keep name/contact information in the document body, use familiar section headings, consistent dates and readable text, and preserve a predictable extraction order. Optional creative portfolio presentation can be separate from the ATS document. These are implementation recommendations inferred from the vendor and career-service guidance, not measured universal ATS compatibility.

Scanned PDFs require a distinct OCR path and user correction. Tesseract.js runs OCR locally in Node/browser workers but does not accept PDF files directly; pages must first be rendered to images. OCR output must remain unverified until reviewed. An explicit “scan detected; review or provide a text document” result is safer than hallucinating extraction success. [Tesseract.js scope](https://github.com/naptha/tesseract.js).

For a native/local-first architecture, these parsers can sit behind a local document worker/sidecar with identical contracts in the retained API. That is an architectural recommendation, not an existing desktop integration. Bind input size, page count, decompressed DOCX size, execution time, output length and network/file access. Validate file signatures rather than trusting extensions. Worker isolation and parser failure messages must be tested against malformed files and zip bombs; package documentation does not provide production safety automatically.

## Grounding and saved artifacts

Recommended pipeline: source bytes and hash → bounded extraction with page/paragraph references → editable candidate facts → user-confirmed fact version → job requirements → select/reorder evidence → optional wording proposal → deterministic validation → review diff → layout → PDF/text extraction verification → immutable saved artifact and manifest.

Separate extracted text from confirmed facts. Employer names, role titles, dates, education, licenses, technologies, numbers and ownership claims should originate in candidate facts. A deterministic selection mode can safely tailor ordering and emphasis without a language model. A rewrite mode cannot obtain a universal factuality guarantee from JSON validation or a keyword allowlist: changed verbs can inflate responsibility even with identical numbers. Preserve the original assertion alongside any proposed rewrite, link its claim IDs, flag unsupported changes and require review. Never fabricate a metric merely because the job values measurable outcomes.

Save the PDF bytes with content hash, candidate fact-version hash, job snapshot hash, template version, selected claim IDs, model/runtime/version if used, generation options and review state. Application authorization must bind that exact artifact hash, not a mutable path called `resume.pdf`. These are Pursuit design recommendations; they are not a claim that a vendor requires this metadata.

## Small-model and token-efficient execution

Local Ollama `/api/chat` accepts a JSON schema in `format`, `stream: false` and generation options. Its structured-output guidance recommends reusing the schema for response validation and low temperature, including zero. Its cloud service currently does **not** support structured outputs, according to that capability page. Distinguish local Ollama capability from every possible hosted Ollama route. A valid schema does not establish that the content is true. [Structured outputs](https://docs.ollama.com/capabilities/structured-outputs).

Ollama chat responses expose prompt/output evaluation counts and durations, making actual request cost/latency observable even when local inference has no provider invoice. `keep_alive` controls model residency. Thinking support and values are model-defined and discoverable through `/api/show`; do not send unsupported blanket settings. Context consumes memory, so a larger declared window is not automatically efficient. [Chat contract](https://docs.ollama.com/api/chat), [context/memory guide](https://docs.ollama.com/context-length).

Recommended execution policy: deterministic extraction, field normalization, exact fact validation, job retrieval, PDF layout, hashes, duplicate checks and routine form mapping; no LLM for these steps. Send only selected candidate facts, relevant job requirements, a short tone profile and a small output schema for a wording task. Cache by all input/model/template versions, cap input and output, limit repairs, and fail to review rather than looping indefinitely. Do not include raw PDF base64 or an entire application history in each prompt.

Test each installed model against the same hallucination, Unicode, truncation, prompt-injection and factual-preservation cases. No source reviewed establishes that a particular Qwen, GLM or other mid-sized model performs every Pursuit task reliably. Model names and quantization alone are insufficient compatibility evidence. “Runs locally” does not mean no electricity, hardware, latency or memory cost.

## Runtime naming and remaining unknowns

The current `apps/api/src/model-gateway.ts` calls fixed OpenAI, Anthropic, Gemini and OpenRouter endpoints and returns strings. Its `hermes` option filters OpenRouter model IDs; that is **not** a Hermes Agent runtime integration. Hermes Agent is a separate project with its own execution environment. Keep model-provider support and agent-runtime qualification separate. [Current Hermes Agent repository](https://github.com/NousResearch/Hermes-Agent).

Not verified here: a live private Google Docs import/export; actual ATS parser interpretation of a generated Pursuit PDF; a specific small local model benchmark; cross-platform native document worker packaging; PDF/UA conformance; runtime integration of Hermes Agent; or a guarantee that source-file extraction preserves every unusual PDF/DOCX design. Each needs executable evidence before being labelled working.

## Portable renderer/extractor option: pdf-lib + unpdf

For the planned shared browser/native React and Node implementation, **pdf-lib is a more direct portable renderer candidate than a server-only process**. Its first-party documentation describes a pure-JavaScript implementation without native dependencies, including browser, Node and React Native use. `PDFDocument.create()`, `addPage()`, `drawText()` and `save()` produce PDF bytes that the harness can download as a Blob while the service stores the same bytes. Browser support is not evidence that Pursuit's Tauri bundling, CSP or download bridge has already been qualified. [pdf-lib platform and creation contract](https://pdf-lib.js.org/).

Custom-font embedding uses `@pdf-lib/fontkit`: register it with `pdfDoc.registerFontkit(fontkit)`, then `embedFont(fontBytes)`. `widthOfTextAtSize` and `heightAtSize` support measured layout; `getCharacterSet()` identifies supported Unicode code points. The renderer must supply wrapping, pagination and missing-glyph handling explicitly, and re-extract emitted text to check content/order. Creating a PDF with text is not PDF/UA certification. [Font embedding example](https://pdf-lib.js.org/#embed-font-and-measure-text), [PDFFont measurements and character coverage](https://pdf-lib.js.org/docs/api/classes/pdffont).

The unpdf usage contract is `getDocumentProxy(new Uint8Array(bytes))`, followed by `extractText(pdf, { mergePages: false })`, which returns `totalPages` and one string per page. With `mergePages: true`, it returns a combined string. Its documented defaults can be overridden with PDF.js options. `extractText` processes all pages; check `pdf.numPages` before calling it. The README explicitly leaves resource limits to callers, notes unrestricted image size by default, and says serverless parsing runs on the event loop. A timeout race alone cannot forcibly stop blocked synchronous CPU work; a terminable worker/process is the stronger boundary. Node rendering to PNG additionally needs a canvas package; browser rendering can use its canvas. These are independent from text extraction. Pin and inspect the installed version because README `main` can move. [unpdf API and untrusted-input guidance](https://github.com/unjs/unpdf), [actual page fan-out implementation](https://raw.githubusercontent.com/unjs/unpdf/main/src/text.ts).

For a lean DOCX route, fflate is also portable between browser and Node. Its ZIP API can filter entries before decompression, and streaming APIs let the application count emitted bytes and terminate. The project warns that ZIP size fields can be absent. Engineering recommendation: whitelist required Word XML parts, bound entry count and declared sizes, enforce actual emitted-byte totals, reject external entities/relationships, and do the parse in a terminable worker. A `filter` on declared `originalSize` alone is not a complete zip-bomb defense. Replacing Mammoth with XML extraction trades dependencies for responsibility over Word paragraph/tab/break/ordering semantics; fixtures must check those explicitly. [fflate ZIP/filter/worker contract](https://github.com/101arrowz/fflate).

## Bundled Noto Sans licence and coverage

Google Fonts' Noto Sans distribution includes SIL Open Font License 1.1. It permits bundling and embedding the font with software, requires preserving copyright/licence notices with redistributed font software, prohibits selling the font by itself, and imposes conditions on modified font naming. Documents created using the font do not have to adopt the font licence. Bundle the licence alongside the exact font files rather than citing a moving download alone. [Noto Sans OFL source](https://raw.githubusercontent.com/google/fonts/main/ofl/notosans/OFL.txt).

Noto Sans should not be called universal Unicode coverage: the upstream family here is maintained in the Latin/Greek/Cyrillic repository, while other scripts use additional Noto families. Check the actual embedded font's supported character set and test candidate names and resume text; fail visibly or use a properly licensed fallback rather than silently deleting characters. [Noto family repository](https://github.com/notofonts/latin-greek-cyrillic), [pdf-lib character-set API](https://pdf-lib.js.org/docs/api/classes/pdffont#getcharacterset).
