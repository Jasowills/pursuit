# Job discovery source foundation

Verified 23 October 2026 against first-party documentation. This is a candidate-facing, read-only sourcing design; no employer account, candidate submission, or external write is required for the public ATS adapters. Recommendations below are engineering judgments, distinguished from documented capabilities.

## The coverage boundary

Public ATS APIs enumerate published jobs **inside a known employer board**. Greenhouse requires a board token; Ashby a job-board name; Lever a site name and region; Workable an account subdomain. None of the four public interfaces below documents a worldwide employer-board directory. A few hundred configured boards cannot justify an “all jobs worldwide” promise. Coverage requires a separate board discovery system, plus adapters for employers using other systems.

Recommended registry: employer identity/domain, career URL, provider, board identifier/region, discovery URL/method, employer-link verification, first/last seen, last successful complete poll, next poll, status, and errors. Seed from user target employers, existing vetted configuration, official career-page links, and permitted web-search results. Accept community hiring lists as leads; confirm their employer links before promotion.

Maintain a deduplicated discovery frontier of employer domains, career URLs, board candidates, and job URLs. Track pending/verified/rejected/retry states, evidence and budgets. Separate frontier work from recurring polling so adding breadth never prevents existing employers from refreshing. Recheck redirects and ATS migrations. Report coverage by verified boards, geography, occupation and last successful refresh, with visible gaps.

## Freshness, trust and duplicates

Recommended shared output contract: provider/board/native ID; employer identity; source/detail/apply/canonical URLs; original title/description; structured and raw locations; remote eligibility; employment type; compensation with currency/unit; source dates and meanings; first-seen, last-seen, last-verified; retrieval outcome; content hash; source evidence and parser version. Every adapter must return completeness and failures separately from jobs. An error or truncated page must never masquerade as an empty successful board.

Use active/closed/unknown verification states. Revalidate before application handoff; an HTTP 200 alone is insufficient. Past `validThrough`, 404/410, explicit closure and an unavailable application flow are closure evidence. Google requires job-detail markup rather than list-page markup, accurate visible content and actionable application access; expired jobs should lose markup, expire dates, or return 404/410. Fully remote does not mean worldwide: preserve applicant location restrictions. Google’s Indexing API submits publisher URLs; it is not a public job-search API. [Google guidance](https://developers.google.com/search/docs/appearance/structured-data/job-posting).

Recommended polling: bounded per-host concurrency, caching/conditional reads where supported, backoff/jitter for 429/5xx, and configurable budgets. Close missing jobs only after a successful complete board snapshot, with confirmation/grace for unstable sources. Preserve first-seen separately from employer publication/update timestamps and search-index freshness filters.

Deduplicate exact provider identities first, then canonical employer job URLs and explicit requisition IDs. Cluster likely cross-source matches using employer, title, location and description evidence; retain all provenance. Do not merge solely by title: separate locations, requisitions, languages, reposts and evergreen roles create legitimate near-duplicates. ATS migrations can replace IDs; no universal cross-ATS job identifier exists in these documented contracts.

## Cross-career discovery

Use broad occupation families and multilingual synonyms, not a software-only title filter. ESCO provides preferred/alternative terms across 28 languages and an ISCO-08 hierarchy covering professionals, trades, services, agriculture, operators and other occupations. Map with confidence and retain original title/department; allow unknown and multiple candidate classifications. [ESCO occupations](https://esco.ec.europa.eu/en/classification/occupation_main). Schema.org also supports coded occupational categories; absence must not exclude a job. [JobPosting definition](https://schema.org/JobPosting).

Uncertainties: public ATS documentation is primarily written for employer career-site builders; endpoint accessibility does not establish unrestricted commercial redistribution rights. Confirm provider terms, licensed-search storage rights and intended volume before scaling. This review establishes documented contracts, not live guarantees across every employer board, historical completeness, or worldwide recall.
